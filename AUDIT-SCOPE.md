### Scoped in — the off-chain enforcement layer

The contracts do not enforce their guarantees alone; they trust values produced off-chain. A contract-only audit can verify that an attestation's signature is valid while leaving open whether the signer attested to the right count — so the code that produces and checks those values is in scope for this engagement:

| Module | What it enforces | Why it is in scope |
|---|---|---|
| `src/lib/countAttestation.ts` + the issuance endpoint `POST /api/launch/count-attestation` (`src/api/launchVerify.ts`) | The **count-attestation signer**: reads the backend's own counted total from the push counter and signs the EIP-712 `CountAttestation` (escrow, repoId, vault, countedTotal, issuedAt, expiry, nonce) with the oracle key. It attests only the true count, never a requested one; nonces come from a per-repo counter; TTL 300s. (Landed with the round-4 commit.) | This is the sole source of the baselines `FeeStreamEscrow` verifies. If it signs the wrong total, binds the wrong vault, or leaks/reuses nonces, the on-chain verification is sound and the guarantee is still false. |
| `src/api/launchVerify.ts` (prepare-launch) + `src/lib/launchRecognition.ts` | **Prepare-launch binding checks**: canonical vault implementation codehash, every immutable vault binding (repo, launcher, escrow, WETH, Bankr claim ledger), the registrar's pre-launch fee-grant check, and the registration-time recognition binding (prepared record, lock-event matching, launch-recipient matching). | These checks are the only thing standing between a user and a signed launch that routes fees to a wrong or unusable vault; registration-time checks run after the launch may already be signed. |
| `src/lib/env.ts` + `src/lib/chains.ts` | **Deployment configuration**: the env surface that sets the treasury wallet (`PLATFORM_REWARD_TREASURY_WALLET`), per-chain escrow and FeeStreamEscrow addresses, Bankr fee/claim ledger addresses, WETH, and how the oracle private key is loaded and handled (`ORACLE_PRIVATE_KEY`). | Every binding check above compares against these configured values. A mis-set or mishandled config silently re-points the platform's trust; key handling is part of the oracle trust assumption (§2, items 1–2). |
| `src/oracle/feeLock.ts` + `scripts/fee-release-sweep.ts` + `scripts/fee-lock-keeper.ts` | **The release worker**: records durable pending-fee-release entries, retries them on the next counted push and from the sweep, clears an entry only when the escrow reports zero vested-and-unpaid at the target count, and drains backlogs with repeated capped `releaseFee` calls — no new pushes required. The keeper fetches attestations and runs claim → lock. | Round-4 blocker 2 was exactly this layer: a successful transaction that leaves vested fees unpaid, with the queue entry cleared, strands user funds with no follow-up. The drain-until-settled logic is a funds-availability guarantee, not plumbing. |

**Priced separately:** the broader GitHub webhook/verifier pipeline and the swarm review system. They decide *whether work counts*; the layer above decides *what the contracts are told and paid*. A firm may quote the GitHub/swarm review as an optional separate line item; it is not required for this engagement and must not be bundled into the fixed fee below.

### Does any beta route still use v1? — code-verified answer

Checked against the source (2026-11-26 working tree), because the v1 add-on price depends on it:

- The backend resolves **one escrow per chain from deployment configuration** — `src/lib/chains.ts` (`escrowAddress`: Base from `GIT_ESCROW_ADDRESS`; Robinhood from `GIT_ESCROW_ROBINHOOD_ADDRESS`, defaulting to the current RH deployment `0x706038b47ba6d0CC69479bB286d064137B50f6Ae`, with the legacy streaming-only deployment remapped to it). There is no per-grant escrow version and no separate v2 address setting anywhere in `src/`.
- **Registration** validates a grant's lock by matching the lock receipt's event to that chain's configured escrow (`src/api/register.ts`) — a new grant can only register against the configured escrow.
- **The release path services grants per stored chain, not per contract version**: `triggerReleaseIfMilestone` (`src/oracle/releaseOracle.ts`) resolves the escrow from each grant's stored `chain` and calls `release()` for every active grant on that chain — and it explicitly handles the legacy contract's different semantics ("Legacy deployed contract: release() leaves tokens on oracle — forward now"). The production backend therefore **services the existing v1 grants today**, including the PODX lock on Base v1.
- GitEscrowV2 is **not deployed on any chain yet** and has no config slot of its own. "New beta grants land on v2 only" becomes true at deployment time, when `GIT_ESCROW_ADDRESS` is pointed at the v2 deployment — it is a configuration fact, not a separate code path.

**Answer: yes — a production route still uses v1.** The servicing/release route for all pre-existing grants (Base and Robinhood Chain) runs against the v1 deployments, and it keeps running after the beta launch repoints registration to v2, for as long as those grants are active. That is why §5 prices v1 as a separate add-on line rather than letting it fall out of scope: excluding it is a decision Gregory makes with this answer in front of him, not a default.

## 2. Trust assumptions to hand the auditor (verbatim list)

1. **The oracle is a single backend signer and its counts are authoritative.** `GitEscrowV2.release` and `FeeStreamEscrow.releaseFee` trust `msg.sender == oracle` carrying a push count; there is no on-chain proof a push happened. `ShipRewards.pay` likewise trusts the oracle's word that a merge counted. A compromised or malicious oracle can release everything releasable and drain the reward pool to arbitrary recipients. This is a named, accepted trust assumption, disclosed to users in BETA.md.
2. **The owner can rotate the oracle** (`setOracle` on all three fund-holding contracts). Owner-key compromise is therefore equivalent to oracle compromise. The same rotation is also the GitHub-death recovery mechanism (backup verifier recounts from the recorded push log and is rotated in), so it cannot simply be removed; the auditor should assess it as a designed, disclosed centralization point.
3. **The ShipRewards owner can withdraw the pool and change the reward token** (`withdraw`, `setRewardToken`). Deliberate (pool closure/migration), but it means reward funds are owner-custodied, not trustless.
4. **The registrar (FeeStreamEscrow owner) registers fee grants** and validates vault bindings at registration. A bad registration binds a repo to the wrong vault/recipient; registration is once-per-repo.
5. **The keeper is permissionless by design.** Anyone may run claim → lock. It can never receive or redirect funds (vault outbound paths are only the immutable ledger and escrow); the worst a hostile keeper can do is trigger locks early, which the attested baseline is designed to make harmless.
6. **FeeLockVault has no admin at all.** Its escrow, fee token, repo, launcher, and claim ledger are immutable at construction. Deployment correctness (right bindings, approved implementation, checked via the canonical masked-template codehash) is therefore part of the security model and happens off-chain at prepare-launch.
7. **Round-4 attestation model (new, specifically needs auditor attention):** tranche baselines are set from an EIP-712 attestation signed by the oracle over the backend's counted total, verified and nonce-consumed in `FeeStreamEscrow`. The auditor should probe replay, staleness/monotonicity, cross-repo and cross-vault attestation reuse, and what a withheld or delayed attestation does to tranche vesting.
8. **Streaming locks keep custody with the recipient** (`lockAllowance`, `lockWithPermit` in GitEscrowV2): the escrow pulls per milestone at release time, so a recipient who revokes allowance or moves tokens mid-grant can make a release fail. The auditor should confirm failure modes are safe (no partial state corruption, no other grant affected).
9. **ERC-20 assumptions:** contracts use SafeERC20 and OpenZeppelin Ownable/ReentrancyGuard, Solidity ^0.8.24. Fee-on-transfer, rebasing, and callback tokens are not specially handled; grants are expected to be standard ERC-20s and Bankr-launched tokens (including DERC20 variants with transfer restrictions, which motivated the streaming model).
10. **Off-chain counting rules are the real anti-gaming layer** (push verifier: production branches, minimum meaningful change, daily cap of 3, cooldown, duplicate-SHA rejection; swarm: 2 independent PASS quorum, FAIL veto). The contracts assume the backend enforces them. The four Codex review rounds (§3) document where earlier versions of these claims were wrong.

## 5. Recommendation

**Best fit: the boutique / managed tier — one private, fixed-fee audit from a boutique firm or a Cantina managed review, with a Sherlock private contest as the priced alternative. Not top-tier, not solo.**

Reasoning, specific to this launch:

- **What is being protected:** other people's locked tokens and fee streams, in a beta whose entire pitch is "your lock cannot be cancelled and releases only on verified work." A contract bug here does not just lose money, it falsifies the product's one claim. That rules out the solo tier as the *only* review: the novel logic (oracle-signed baseline attestations, the settled-cursor release loop, streaming allowance pulls, a vault whose only defence is its immutable bindings) deserves more than one reviewer's blind spots, and tester recruitment will lean on the report.
- **Why not top-tier:** at ~666 nSLOC the scope is small. The sourced anchors ($25k per engineer-week, 4–12 week queues, medium-engagement bands starting around $50k) buy brand and depth sized for high-TVL protocols. The queue alone could add a quarter to the launch calendar, and nothing about this codebase needs their specialist areas (no ZK, no cross-chain, no novel cryptography beyond standard EIP-712).
- **Why boutique/managed works:** the sourced bands (boutique $15k–$60k [2][3]; Sherlock's mid-DeFi band $40k–$100k as the ceiling reference [1]) come with named senior reviewers, a written report, and a fix-verification pass, on a 2–4 week clock that fits between the round-5 freeze and deployment. Sherlock's model adds one thing the others do not: optional post-audit coverage priced at 2% of covered TVL [5], which is a real option once user value is actually locked.
- **Sequencing is not optional:** engage **after** Codex round 5 clears and the code is frozen, **before** any production deployment. The round-4 edits prove the point: FeeStreamEscrow changed materially three times in two days. An audit started today would be obsolete before the report arrived. Budget one remediation pass from the start (Sherlock's reference: $5k–$20k per pass [1]; contest fix reviews have publicly run ~$6k [10]) instead of treating findings as a surprise.
- **After launch, add the second layer:** a standing bug bounty (e.g. Immunefi) once real value is locked. The DF3NDR reference states the realistic minimum for a new mainnet launch as one firm or independent audit **plus** a bug bounty [5]. The bounty is a post-launch decision and is not part of this engagement's budget.

**Quote structure (required in every request — see `QUOTE-REQUESTS.md`):** quotes are requested on one fixed structure so the prices are comparable and the remediation loop is not a surprise change order:

- **One fixed fee** covering, as named line items inside that fee: the **named reviewers** who will do the work (names or senior-researcher identities, not "the team"), the **written report**, and **one fix-verification (remediation) pass** against a **pinned commit** — we remediate findings, the same reviewers verify the fixes on the pinned remediation commit, and that pass is included in the fee, not quoted later.
- **v1 `GitEscrow.sol` is a separate add-on line**, priced apart from the main fee (see the code-verified answer in §1: the production servicing route still runs on v1 for existing grants). Gregory accepts or declines the add-on explicitly; it is never bundled silently and never assumed excluded.
- **The off-chain enforcement layer (§1) is inside the fixed fee.** The broader GitHub webhook/verifier and swarm review is an **optional separate line item**, quoted apart if the firm offers it.

## 5A. Production claim readiness — funded treasury; paymaster out of scope

The PODT run (§1) exposed an operational fact the audit does not cover but the beta depends on: Bankr claims are beneficiary-signed, so **the first production claim must come from a funded treasury**. The freshly designated treasury held 0 ETH and could not claim until the test launcher sent it a 0.00005 ETH gas stipend. In production there is no stipend fairy:

- **The treasury is funded ahead of claims.** The platform operator — fren, operating under Gregory's ownership — is responsible for **monitoring the treasury wallet's Base ETH balance and funding its gas** before any production claim is due, as a standing operational duty, not a per-claim decision. (Treasury: `0x9F1019CC208eD1786a85d19C616A017cd1cB5291`, the 25% platform fee recipient on every platform launch.)
- This is an operations commitment, not audit scope: no auditor deliverable covers whether we remembered to fund a wallet. It is recorded here so the beta checklist carries it next to the audit, where it belongs.

**The sponsored-claim paymaster is outside this audit and is not a beta dependency.** The token-funded paymaster idea (launch fees sponsoring other recipients' claim gas) remains designed-not-built. *Conditional add-on, if it ever ships:* a paymaster that pays other people's gas is a new authorization and funding surface — who may sponsor, whose claims qualify, spend caps, funding source, and drain/refund controls.
